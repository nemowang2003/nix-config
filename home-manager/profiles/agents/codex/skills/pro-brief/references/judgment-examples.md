# 判断示例：采访到什么程度、何时交给 Pro

这些是虚构情景，用于校准决策，不是应套用到真实用户身上的需求或实验结果。只读与当前情况相关的示例。

## 代用户约稿：从模糊题目到明确成品

用户：“帮我找 Pro 写一份公司知识库方案，尽量一次搞定。”

第一轮先问两件事：方案给谁看、看完要做什么决定；现有资料和最头疼的问题是什么。与此同时，读取用户已提供的说明，找出资料类型和现状，不急于选择技术栈。

用户回答：“给老板决定要不要试点。我们 30 人，主要用网盘和聊天找资料，新人总是找不到最新流程。”

第二轮基于这个回答问会改变方案的取舍：“试点有没有预算和数据外发限制？”“愿意先试一个部门，还是必须全公司上？”不再问已经确认的读者和用途。

用户回答：“先做客服部门，四周内看到效果；人事资料不能外传，暂不定产品。”

Codex 可以检查少量现有文档，判断是否存在版本和权限问题；无需搭好知识库或先完成产品选型。若没有访问权限，标明“用户描述，未抽样核验”。剩余价值是 Pro 的方案综合，已经可以约稿。

委托核心可以写成：

> 请写一份供老板决定是否启动客服知识库试点的完整方案。公司 30 人，目前通过网盘和聊天找资料；用户反映新人难以找到最新流程，此问题尚未量化验证。试点范围是客服部门，希望四周内能观察成效；人事资料不得外传，尚未指定产品或预算。
>
> 请交付可直接提交的方案，包含目标与范围、内容责任和版本机制、四周计划、试点成效的测量办法及继续／停止的判断标准。给出推荐路径及适用前提。预算未定，请用少量投入情景说明关键取舍，不虚构报价。工具选型仅比较满足约束的能力类别；如引用具体产品的现行信息，请核实并注明来源。

这份约稿需要的是完整决策材料，不能只要求“给我一个目录”。也不必继续问每种字体或把所有文档清点完。

## Codex 自己求助：竞争性解释尚未区分

情景：同步程序在并发重试时偶尔重复创建记录。用户最终要的是可靠修复，不是证明某个缓存有错。

有价值的初查是读取请求处理与写入代码，核实幂等键的生成和使用位置，做一个能区分串行与并发行为的小复现。保留输入、命令、版本及实际输出；成功和失败样本一起记录。

若观察表明串行重复请求未造成重复，并发重复请求会产生重复，这只能缩小调查范围，不能单凭它断言“数据库一定有竞态”。委托要保留其他可能性，例如键的作用域不同，或外部副作用不在保护范围内。

此时可委托 Pro 分析可能的执行时序、推荐最小修复、说明机制保证的边界，并提供针对性验证方案。Codex 不必先重构整个系统。交付材料必须包含关键代码与真实复现结果，不能只留下本地路径或写“附件见仓库”。

若一个检查已经发现并修复了错误字段名，且相关验证通过，常规问题就已解决。除非用户仍要专家复核，不应为了符合流程再调用 Pro。

## 用户需要一篇作品：探索不是先替专家写完

用户：“我要 Pro 写一篇关于远程工作的演讲稿，先帮我把要求理清。”

先澄清听众、场合、时长和演讲希望改变的看法；再根据回答了解立场、可用经历、不能公开的内容和风格参照。用户不确定风格时，给两小段有差异的开场作比较，比再问一遍“想要什么风格”更有效。

核对用户提供的故事能否使用，标清未经核实的数字。信息足够后委托完整演讲稿，附转场、结尾和适合口头表达的要求。不要花大量时间自己写完整篇章，再让 Pro 只改几个词；也不要为文学创作强行安排代码实验或大规模资料检索。

## 无法一次闭环：保留诚实的条件

用户希望 Pro 根据实验结果选方案，但真正决定优劣的长期数据尚未产生。多问几轮偏好也不能创造数据。

先做能在当前资源下完成的小检查；若剩余证据必须等待长期实验，委托 Pro 交付条件化决策、实验设计与结果判读规则，使用户拿到数据后能自行选择。明确最终结论依赖尚未产生的证据，不许为了“一次完成”写成已经证实。

若不可缺的资料已有现成文件但未提供，先集中请求这些资料。能够独立推进的部分继续做；不能把“等了一段时间”当成用户已接受某个高影响假设。

## 收到回复后：只为新增专家难点补问

Pro 给出了可用方案，但格式与用户要的文档不同：由 Codex 转换并核对内容，不花一次消息要求重新排版。

Pro 推荐的算法在真实边界样本上失败：Codex 先确认调用方式与输入符合前提。若仍是专家级问题，把复现输入、实际输出、预期、已验证结论和所有相关未解决问题打包为一条补问。生成补问不自动意味着获准再次发送。
